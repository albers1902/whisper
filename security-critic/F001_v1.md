# Security Critic review F001 v1 (Brugere og login)

Reviewed: spec `product-ai/F001_v1.md`, impact `tasks/impact-F001.md`, the whole diff (App, Users, Session/NativeSessionDriver, Csrf, LoginThrottle, Password, Flags, Request/Response, View, front controller, `.htaccess`, migration, `opret-admin.php`), DECISIONS, and the engineer's v0 last. I did not run the tests. The review is based on reading the code.

## Attack surface and what holds

- **Request order in `App::dispatch`.** The flag check, route, idle timeout, user from the DB, login required, forced password change, admin role, CSRF and controller run in that order. Authorization is evaluated on every request, and the role and active status come from the database, not the session. A downgrade or deactivation therefore takes effect on the next request.
- **Anonymous access.** Anonymous requests to protected routes redirect to `/login` before any existence check, so `/brugere/{id}` does not leak which ids exist. A `user` gets 403 before CSRF on all admin routes, including POST. I found no IDOR: every id is checked against the admin role, and `/konto` only touches the session's own user.
- **Session.**
  - The cookie is `Secure`, `HttpOnly` and `SameSite=Lax`, and `use_strict_mode` and `use_only_cookies` are set.
  - Login does `clear()` and then `regenerate(true)`, which handles session fixation. Logout destroys the session and expires the cookie.
  - The password fingerprint (`pwfp`) logs out other sessions when the password changes or is reset.
  - The session directory is outside `public_html`, with mode 0700.
- **CSRF.** The token is synchronizer-style, compared with `hash_equals`, and every POST form carries it. The logout form has it too.
- **SQL.** All SQL goes through prepared statements, with `EMULATE_PREPARES` off.
- **XSS.** All output goes through `e()` with `ENT_QUOTES`. Numeric ids are cast to int. The CSP is strict (`default-src 'self'`, no inline script or style, `frame-ancestors 'none'`), and `no-store` is set.
- **Passwords.**
  - Hashing uses `password_hash` and `password_verify`.
  - The one-time password comes from `random_bytes` with rejection sampling, which gives about 92 bits.
  - It is shown only in a `no-store` response and is never stored.
  - NUL bytes are rejected.
  - The dummy bcrypt for an unknown e-mail evens out response time. An inactive user is handled as a failure after `password_verify`, so the error and the timing are the same.
- **Last admin.** The check runs in a transaction with `FOR UPDATE` on all active admins and then on the user, always in the same lock order. I found no path that leaves zero active admins. A self-deactivation is blocked.
- **Flag.** `index.php` returns 404 before any session or cookie when the flag is off. An unknown or missing env means everything is off. `/health` is a first `[L]` rule in `.htaccess` and never reaches the front controller.
- **CLI.** It is CLI-only, outside the docroot. The password comes from stdin or a no-echo prompt and never from argv. It exits non-zero on error. `shell_exec('stty …')` takes no user input.
- **Secrets and CI.** I found no secrets in the diff, and `.github/workflows` is not touched.
- **Spec deviation.** The spec says sessions go in `/home/<bruger>/sessions`. The code uses `<home>/var/sessions`, which the engineer flagged. This is acceptable, because the directory is outside the docroot and the permissions are tight.

There are no CRITICAL or HIGH findings. The findings below are accepted.

# Accepted findings

## F001-S1
# Severity
MEDIUM
# Risk
The login throttle can be bypassed with parallel requests, and `/konto` has no throttle at all.
# Exploit scenario
`loginPost` calls `isLocked`, then runs bcrypt (`password_verify`), and only then calls `record`. A burst of N parallel POSTs for the same e-mail all pass `isLocked` before the first failure is written. The attacker gets about as many guesses as there are PHP workers per bcrypt cycle, instead of 5 per 15 minutes. With a stolen session cookie, an attacker can also guess the "current" password unlimited times on `POST /konto` (`accountPost`), and that endpoint has no throttle or lock. Both attacks need either a guessable password or an already compromised session. The password minimum is 12 characters, which limits the practical damage.
# Exact issue
The check and the record are not atomic (`App::loginPost`, `LoginThrottle`). `accountPost` does not use `LoginThrottle`.
# Recommended fix
Record the attempt before the expensive verification and update it to success afterwards, or take an advisory lock per e-mail (`GET_LOCK`). Count failed "current password" attempts in `accountPost` through the same throttle, keyed on the user id.
# Machine check
A concurrency test in `tests/` for the throttle. Semgrep cannot find this.

## F001-S2
# Severity
MEDIUM
# Risk
The throttle depends on an unconfirmed assumption about the client IP, and it can be bypassed with IPv6.
# Exploit scenario
`Request::fromGlobals` uses only `REMOTE_ADDR`. The engineer wrote that they do not know whether a proxy sits in front of Apache on DEV. If there is one, all users share a single IP. Five failures from anyone then lock everyone out, which is a trivial denial of service on login. Over IPv6, an attacker with a /64 block gets a new "IP" per request. The per-IP limit then does not apply, and password spraying across many e-mails is only held back by the per-e-mail limit.
# Exact issue
The IP key is the full `REMOTE_ADDR`, with no normalization of IPv6 and no confirmed network topology.
# Recommended fix
Have sysadmin confirm that `REMOTE_ADDR` is the real client address on DEV (`shared/SERVERKONTRAKT.md`). Then group IPv6 addresses by /64 in `LoginThrottle` (the `ip` column holds the normalized value). If a proxy is added later, solve it with a trusted-proxy list and never trust `X-Forwarded-For` blindly.
# Machine check
None. This is an infrastructure assumption.

## F001-S3
# Severity
LOW
# Risk
Failed logins write rows without a cap, and every login POST runs an unindexed cleanup query.
# Exploit scenario
Every failed attempt inserts a row. Attempts rejected during a lock are not recorded, which limits this per IP. A distributed attacker can still grow `login_attempts` over 30 days. `purge()` runs `DELETE … WHERE created_at < ?` on every login POST. The indexes are `(email, created_at)` and `(ip, created_at)`, so this is a full scan. That becomes a slow query and an amplified denial of service as the table grows. In addition, every request without a cookie creates an empty session file, which is cleaned up with only 1% GC probability.
# Exact issue
There is no index on `created_at` alone, and `purge` runs on every request. The session file is created even for a bare `GET /login`.
# Recommended fix
Add an index on `created_at`, and run `purge` with probability (for example 1%) or from cron. Consider starting the session only when a cookie exists or for `/login`.
# Machine check
None.

## F001-S4
# Severity
LOW
# Risk
bcrypt truncates passwords at 72 bytes, and there is no cap on length.
# Exploit scenario
A long password is silently cut at 72 bytes, so characters after that add no strength. A very long password costs only linear hashing time, since bcrypt truncates, so there is no real denial of service. No HSTS header is set by the app either. HSTS is not part of the serverkontrakt flow (§ line 248), and the cookie has `Secure` set unconditionally, so the risk is limited.
# Exact issue
`Password::problem` has no maximum, and no HSTS header is set.
# Recommended fix
Reject passwords longer than 72 bytes with a message, or pre-hash them. Add HSTS at the server level when the sysadmin side allows it.
# Machine check
None.
