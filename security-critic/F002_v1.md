# Security review F002 v1 — Zendesk Talk, lokal transcription, opkaldsvisning

Reviewet: `git diff main...d6071a1` (47 filer, kun læst via `git show`/`git diff`), spec `product-ai/F002_v1.md`, impact `tasks/impact-F002.md`, `launched/STABLE/DECISIONS.md`. Engineerens `fullstack-ai/F002_v0.md` og `changes/F002.md` er læst sidst.

## Overblik
Den væsentligste angrebsflade er håndteret solidt:
- **SQL:** al SQL er parametriseret. `LIMIT` og `OFFSET` er heltals-castede, og fritekst bygger kun `+ord*` af `\p{L}\p{N}`, så der er ingen boolean-operator-injektion.
- **XSS:** alt dynamisk output går gennem `View::e()`.
- **Lyd:** stien valideres med regex og `realpath` under `var/recordings`. `Range` er parset strengt, og `Cache-Control` og `nosniff` kommer fra `App::secure()`.
- **Adgang:** alle ruter ligger bag F001-login. Ruterne findes ikke, når flaget er slukket (404).
- **Shell:** `proc_open` bruger et argv-array uden shell og uden brugerinput. Lydstien er absolut, så `argparse` kan ikke læse den som option.
- **SSRF og token:** `Authorization` sendes kun til den konfigurerede Zendesk-vært, redirects følges manuelt med vært-tjek pr. hop, og kun https på port 443 uden brugerinfo tillades. Tokenet caches 0600 uden client_secret og klient-id.
- **Logs:** logs indeholder kun opkalds-id.

Ét fund blokerer godkendelse (S1). Resten er MEDIUM/LOW og kan accepteres med beslutninger.

# Findings for Fullstack

## S1 — Cron-scripts ignorerer feature-flaget `F002_zendesk`
# Severity
HIGH
# Risk
Persondata (kunders opkald, telefonnumre, transcripts) hentes og gemmes i et miljø, hvor flaget står `off`. Rollback-påstanden holder desuden ikke.
# Exploit scenario
`whisper-cron.sh` lægger cron-linjerne i sitets crontab. På TEST eller STABLE (`test = off`, `stable = off`, DECISIONS #4: kun DEV) kan en `[zendesk]`-sektion i `config.ini` plus den crontab-linje være nok til, at `zendesk-sync.php` henter alle opkald siden `since`, og at `transcribe.php` transcriberer dem. Ruterne er 404, men data samles i `var/recordings` og databasen uden at kunne ses eller styres. Selve rollback-trinnet i `changes/F002.md` ("Rollback: stable = off") stopper heller ikke hentningen. Spec'en siger, at `dev = off` er rollback.
# Exact issue
`git grep Flags` i `homedir/cron/` og `homedir/src/Zendesk|Transcription` giver ingen træf. `zendesk-sync.php` og `transcribe.php` tjekker kun `logs/deploying`, lock og config. Reviewreglen kræver, at kodestien ikke er nåbar med flaget slukket. `whisper-setup.sh` og `zendesk-probe.php` er ikke flagbundne. Det er acceptabelt for setup, som ejeren kører manuelt.
# Recommended fix
- Efter `require Bootstrap.php` i `zendesk-sync.php` og `transcribe.php`: hvis `!Flags::enabled('F002_zendesk')`, så `exit(0)` før lås, heartbeat, DB og netværk. Tjek også `F001_brugere`, hvis flagene skal være afhængige.
- Tilføj en test til AK9: flag off giver at begge scripts afslutter uden DB-skrivning (ingen `sync_state`-række, ingen status-ændring).
- Ret rollback-linjen i `changes/F002.md`, så den passer til adfærden.

## S2 — Transcription-motoren har ingen tidsgrænse; ét hængende job stopper køen
# Severity
MEDIUM
# Risk
Driftsstop af transcription (availability).
# Exploit scenario
`proc_close()` i `ProcessEngine` venter uden grænse (bevidst efter spec: lange opkald). Hænger Python eller PyAV på en korrupt lydfil, holder `transcribe.php` lock'en for evigt. `resetStale()` kører kun med lock'en, så "hængende job sat tilbage efter 2 timer" (AK4) kan aldrig ske i netop det scenarie. Alle senere opkald står som `ventende`.
# Exact issue
Ingen watchdog. 2-timers-reglen forudsætter, at processen dør af sig selv.
# Recommended fix
Lav en hård øvre grænse uden at afvise lange opkald, fx timeout = max(2 t, 4 × varighed) med `proc_terminate`/`SIGKILL`. Alternativt kan `resetStale` bruge en `flock`-probe på en separat heartbeat. Accepteres den, så skriv den som risiko med udløb.

## S3 — Zip-download: ubegrænset ressourceforbrug for enhver indlogget bruger
# Severity
MEDIUM
# Risk
Autentificeret DoS (hukommelse, disk, CPU).
# Exploit scenario
`/opkald/download` uden filter henter op til 2000 rækker inkl. `MEDIUMTEXT` `text` og `segments_json` i ét `DB::all`, bygger hver `.txt` i hukommelsen og skriver zip'en til `var/tmp`. Gentagne kald (eller `side=100000`, dyrt OFFSET på listen) kan tage `memory_limit` eller disk. Der er ingen rate limit, og alle roller kan kalde den.
# Exact issue
`CallPages::zip` og `Calls::forZip` bruger ingen paginering eller streaming og har ingen throttle. `cleanTmp` rydder først efter 1 time.
# Recommended fix
- Hent og skriv rækkevis i batches (fx 100).
- Begræns samtidige zip'er med en lock eller en simpel throttle pr. bruger.
- Klip `side` til ≤ total sider.

## S4 — Ingen sporbarhed på masse-eksport af persondata
# Severity
LOW
# Risk
Alle roller kan hente alle opkaldslyd og transcripts uden spor af hvem, hvad og hvornår (GDPR-ansvarlighed). Det følger af spec'ens "alle indloggede ser alle opkald", men der er ingen log.
# Exact issue
Lyd, `.txt` og zip logger intet. Retention og sletning er ud af scope og står i impact som åben risiko.
# Recommended fix
Log én linje pr. lyd-, txt- og zip-hentning med bruger-id og opkalds-id, uden PII. Registrér retention som risiko med udløb før STABLE.

## S5 — OAuth-scope er som standard bredt `read`
# Severity
LOW
# Risk
Spec'en siger "kun read-scopes (tickets og voice)". Standard er `read`, som giver læseadgang til alle Zendesk-ressourcer. Klientens secret ligger kun i `config.ini` (0600), men et lækket token kan læse mere end nødvendigt.
# Exact issue
Engineerens v0 skriver selv, at der ikke findes noget voice- eller Talk-scope, og at målingen (`zendesk-probe.php`) afgør det. Koden afviser korrekt tomt scope og alle write-scopes.
# Recommended fix
Efter proben: indsnævr standard til `tickets:read users:read`, hvis Talk-exporten virker med det. Ellers accepter `read` med en begrundelse. Sæt "allowed scopes" på selve OAuth-klienten i Admin Center.

## S6 — Supply chain i whisper-setup
# Severity
LOW
# Risk
`faster-whisper==1.1.1` er pinnet, men transitive afhængigheder (PyAV, ctranslate2, huggingface_hub, onnxruntime m.fl.) er ikke pinnet eller hash-låst. Modellen hentes uden fast revision. Alt kører som sitets bruger, som også ejer `var/recordings` og `config.ini` med client_secret.
# Recommended fix
Brug en `requirements.txt` med `--require-hashes` (eller `pip freeze`-låsning), pin model-revision (HF commit-hash), og skriv det som accepteret risiko, hvis det udskydes. Transcription kører med `HF_HUB_OFFLINE=1`, så der går ingen kald ud under kørsel (godt).

## S7 — Download uden størrelsesgrænse
# Severity
LOW
# Risk
En unormalt stor optagelse (Zendesk-side fejl) fylder disk.
# Exact issue
`CurlTransport` sætter 1800 s timeout, men ingen `CURLOPT_MAXFILESIZE_LARGE`.
# Recommended fix
Cap fx 500 MB.

## S8 — URL-parser-differential (defense in depth)
# Severity
LOW
# Risk
`hostOf()` bruger `parse_url`, mens curl parser selv. Jeg fandt ingen udnyttelig variant: bruger-info afvises, værten skal være et eksakt match, og kun https/443 tillades. Kun defense-in-depth.
# Recommended fix
Afvis URL'er med kontroltegn, `\` eller mellemrum, før `parse_url`.
