## Status of v1 findings

- **F001-S1 (throttle race, /konto unthrottled): fixed.**
  - `LoginThrottle::begin()` writes the attempt as a failure before bcrypt and counts only rows with a lower id. A burst of N parallel requests lets at most about 5 through.
  - A locked attempt is deleted again, so the lock still expires on time and cannot be extended indefinitely.
  - `succeed()` flips only its own row.
  - `accountPost` now uses `begin()` keyed on the user's e-mail and IP, and CSRF is checked before it. A wrong "current password" returns 422 and stays counted.
  - A new test in `test_F001-AK3_throttling.php` covers this.
- **F001-S2 (IPv6 bypass): partly fixed.**
  - `normalizeIp` groups IPv6 by /64 and stores IPv4-mapped addresses as IPv4. The value fits in the `ip` column (45 characters).
  - The proxy assumption is still unconfirmed (see the accepted finding below).
- **F001-S3 (unindexed purge, empty session files): mostly fixed.**
  - `created_at` has an index, and `maybePurge` runs at roughly 1 in 50 login POSTs.
  - `index.php` now creates a session only when a cookie is present or the path is `/login`. Other anonymous requests use `ArraySessionDriver` and redirect, 404 or 403.
  - `last_seen` is written only for logged-in users.
  - A request with an arbitrary garbage cookie value still creates a session file (see the accepted finding below).
- **F001-S4 (72-byte cap): fixed.** `Password::problem` rejects more than 72 bytes with a clear message. HSTS remains an accepted risk (DECISIONS #9, already written).

# Accepted findings

## F001-S2 (remaining part)
# Severity
MEDIUM
# Risk
The per-IP throttle assumes that `REMOTE_ADDR` is the real client address. This has not been confirmed for DEV or STABLE.
# Exploit scenario
If a reverse proxy sits in front of Apache, every client shares one IP, and five failures from anyone lock everyone out of login. That is a trivial denial of service. The IPv6 part is fixed by /64 grouping.
# Exact issue
`Request::fromGlobals` uses only `REMOTE_ADDR`. The network topology is not confirmed by sysadmin.
# Recommended fix
Ask the sysadmin subagent whether `REMOTE_ADDR` is the client address on DEV and STABLE (`shared/SERVERKONTRAKT.md`). If a proxy is added later, use a trusted-proxy list and never trust `X-Forwarded-For` blindly. The question must be answered before the `stable` flag is turned on.
# Machine check
None. This is an infrastructure assumption.

## F001-S5 (new, from the S3 residue and HEAD handling)
# Severity
LOW
# Risk
Two small residues remain: session files from garbage cookies, and flash messages consumed by HEAD requests.
# Exploit scenario
1. A bot that sends any non-empty `whisper_session` cookie value makes `start()` create a session file. This is bounded by the 1% GC, and it needs a request per file.
2. A HEAD request to a page with a flash message is handled as GET, so a link preview or monitor can consume the flash. Nothing is exposed, and it only affects usability.
# Exact issue
`NativeSessionDriver::hasCookie()` checks only that the value is non-empty, not that it matches an existing session. `flash()` removes the message on HEAD as well.
# Recommended fix
Optional. Check that the session file exists before starting a session, and do not consume flash on HEAD.
# Machine check
None.
