# System understanding

F004: Adversus-opkald i Whisper med auto-transcription af succes-leads. Tier 1, Type: feature.
Branch: `feature/F004-adversus`. Spec `product-ai/F004_v1.md`, impact `tasks/impact-F004.md`, ejerens beslutning
DECISIONS #31 (`launched/STABLE/DECISIONS.md`).

## 1. Hvordan delsystemet virker ende til ende (det, jeg har læst)

**Opkald fra Zendesk (F002).** `homedir/cron/zendesk-sync.php` (cron hvert 10. min via `cron/whisper-cron.sh`) stopper
på `logs/deploying`, kræver flagene `F001_brugere` og `F002_zendesk`, tager `Lock::tryAcquire('zendesk-sync')` og kører
`Zendesk\Sync::run()`. Den gemmer i `calls` med UPSERT på `UNIQUE (source, external_id)`, flytter `sync_state.cursor_value`
kun fremad og henter derefter lyd (`downloadPending()`: kun `source = 'zendesk'`, `audio_status = 'venter'` eller
`fejlet` med < 5 forsøg) til `var/recordings/ÅÅÅÅ/MM/<id>.<ext>` via en `.part`-fil (0600).
Kilde: `homedir/src/Zendesk/Sync.php` (læst hele), `homedir/cron/zendesk-sync.php` (læst hele).

**Tabellerne** (`homedir/migrations/0003_v0.3.0_opkald.sql`, læst hele): `calls.source ENUM('zendesk')`, `external_id
VARCHAR(64)`, `ticket_id NULL`, `direction ENUM('inbound','outbound')`, `customer_phone`, `agent_name`, `started_at` (UTC),
`duration_sec`, `recording_url VARCHAR(500) NOT NULL`, `audio_path`, `audio_status ENUM('venter','hentet','fejlet')`,
`transcript_status ENUM('ventende','transcriberer','faerdig','fejlet')` m.fl. `sync_state(source VARCHAR(20) PK,
cursor_value VARCHAR(255), last_run_at, last_ok_at, last_error)`.

**Køen (F002/H006).** `Transcriber::claim()` tager kun rækker med `audio_status = 'hentet'` og `transcript_status =
'ventende'` (eller `fejlet` efter backoff). Kilde: `homedir/src/Transcription/Transcriber.php` (læst hele). Køen kender
altså ikke kilden: **et opkald er i kø, når lyden er hentet, og status er `ventende`**. Det betyder, at F004 ikke behøver
at røre `Transcriber.php` eller `cron/transcribe.php` (H007 ændrer dem samtidig). Antallet af workers er ligegyldigt, fordi
claim er én atomisk UPDATE pr. opkald.

**Adversus-klienten (F004a).** `homedir/src/Adversus/Client.php` (læst hele): `getJson($path, $query)` mod
`https://api.adversus.io/v1`, Basic auth, ingen automatiske redirects, 429 venter Retry-After/60 s højst 3 gange og kaster
derefter `RateLimited`. `$maxRequests` er et loft over HTTP-kald pr. kørsel (også gentagne forsøg og redirect-hop); nås
det, kastes `RateLimited`. `downloadRecording($callId, $dest)` følger 307 selv, tjekker hver vært mod `HOST` eller
`AdversusConfig::$recordingHosts`, og sender aldrig Authorization til andre værter. `errorText()` renser fejltekster.
`homedir/src/Adversus/AdversusConfig.php` (læst hele): `[adversus] username, password, since (ÅÅÅÅ-MM-DD, tolket som UTC
midnat), recording_hosts, success_status (standard success)`.

**Siderne.** `CallPages::list()` → `Calls::filter()` + `Calls::search()` (`homedir/src/CallPages.php`, `homedir/src/Calls.php`
læst hele). `Calls::where()` er det fælles WHERE for liste, MCP-range og zip. MCP (`homedir/src/Mcp/Tools.php`, læst
`getTranscript` og `stats`) har egne SQL'er i `getTranscript` og `stats`, der ikke går gennem `Calls::where()`.

**Tests.** `homedir/tests/run.php` kører hvert `test_*.php` som én case. `homedir/tests/f002_lib.php` har `FakeTransport`
(svar pr. metode + URL, præfiks med `*`) og `f002_setup()`, der tømmer `calls`, `transcripts` og `sync_state`.
`homedir/tests/f004a_lib.php` bygger Adversus-svar med `FakeTransport`.

## 2. Mapning af Adversus-felter og migrationen `0005_v0.5.0_adversus.sql`

| Adversus | Kolonne | Bemærkning |
|---|---|---|
| — | `source = 'adversus'` | ENUM udvides til `('zendesk','adversus')` |
| `/recordings` `cdr.id` = `/calls` `id` | `external_id` | UNIQUE (source, external_id) giver idempotens |
| `/calls` `leadId` | **ny** `lead_id BIGINT UNSIGNED NULL` + indeks | matchet til succes-leads |
| `/calls` `campaignId` | **ny** `campaign_id BIGINT UNSIGNED NULL` | kun vist/MCP, ingen filtrering (out of scope) |
| `/calls` `userId` | **ny** `agent_ext_id VARCHAR(64) NULL`; `agent_name = ''` | se "Hvad jeg ikke ved" 3 |
| `/calls` `origin` (inbound/outbound) | `direction` | andet end de to værdier → opkaldet springes over og logges med id |
| `/calls` `start` | `started_at` (UTC) | |
| `/calls` `duration` | `duration_sec` | se "Hvad jeg ikke ved" 4 (duration vs. conversation) |
| `/calls` `number` | `customer_phone` (renset som Zendesk: `[0-9+ ]`, 40 tegn) | Zendesk gemmer allerede nummeret (`Sync::saveCall`), så spec'ens regel tillader det |
| `recording.download` (signeret) | **gemmes ikke** | `recording_url = ''`; lyd altid via `/calls/{id}/recording` |
| — | `ticket_id = NULL` | |
| succes | **ny** `is_success TINYINT(1) NOT NULL DEFAULT 0` + indeks | Zendesk-rækker = 0 (filteret behandler zendesk separat) |
| "ikke valgt" | `transcript_status` ENUM udvides med `'ikke_valgt'` | `audio_status` forbliver `venter`, men intet henter den |

Ny tabel `adversus_success_leads (lead_id BIGINT UNSIGNED PK, last_updated_at DATETIME NULL, seen_at DATETIME NOT NULL)`.
Cursorer i den eksisterende `sync_state` (ingen ny tabel): rækkerne `adversus` (last_ok/last_error, vises på siden),
`adversus-rec` og `adversus-leads` (cursor_value). Navnene er under 20 tegn.

Migrationen (`-- reversibel: ja`, `-- destruktiv: nej`, `-- idempotent: ja`): `ALTER TABLE calls MODIFY source ENUM(...)`,
`MODIFY transcript_status ENUM(... ,'ikke_valgt')`, `ADD COLUMN IF NOT EXISTS` × 4, `ADD INDEX IF NOT EXISTS` × 2,
`CREATE TABLE IF NOT EXISTS adversus_success_leads`. Alle er idempotente på MariaDB 10.11. Down (`migrations/down/`):
`DELETE FROM calls WHERE source = 'adversus'` (transcripts følger med `ON DELETE CASCADE`), `DELETE FROM sync_state WHERE
source LIKE 'adversus%'`, derefter ENUM'erne tilbage, `DROP COLUMN IF EXISTS` og `DROP TABLE IF EXISTS`. Down sletter
Adversus-data. Det er nødvendigt, før ENUM'en kan snævres ind, og lydfilerne bliver liggende som ved 0003's down.

**Hvorfor `ikke_valgt` i `transcript_status` og ikke i `audio_status`:** én tilstand styrer både "hent lyd" og "transcribér".
Knappen er så én atomisk `UPDATE calls SET transcript_status = 'ventende' WHERE id = ? AND source = 'adversus' AND
transcript_status = 'ikke_valgt'` og dermed idempotent (AK7). Lydhentningen tager kun `transcript_status <> 'ikke_valgt'`.
`Transcriber::claim()` kræver `audio_status = 'hentet'`, så et ikke-valgt opkald kan aldrig komme i køen ad den vej.
`Calls::status()` tæller i dag `audio_status = 'venter'` som "venter på lyd" og skal ændres til at udelade `ikke_valgt`.

## 3. Algoritmen for cursorer og vinduer (cron `cron/adversus-sync.php`, hvert 10. min)

Rækkefølge pr. kørsel: (a) succes-leads → (b) optagelser og opkald → (c) markér succes begge veje → (d) lydhentning.
Ét `Client` med `maxRequests = 100` deles af alle faser. Fase (b) stopper, når der er under `RESERVE = 30` kald tilbage,
så lydhentningen altid får kald. Ét lyd-download koster 2 kald (307 + S3).

**Filteroperatorer.** Kun `$eq, $gt, $lt, $c, $nc, $neq` (F004a v2, `fullstack-ai/F004a_v2.md`). Der er ingen `$gte`. Alle
nedre grænser er derfor `$gt (t − 1 s)`. Det giver et overlap på højst ét sekund, og dubletterne fjernes af
`UNIQUE (source, external_id)` / PK `lead_id` (UPSERT/`INSERT IGNORE`). "Uden dubletter" gælder altså databasen, ikke
API-svarene.

**(a) Succes-leads, keyset på `lastUpdatedTime`** (filtrerbar og sorterbar, F004a v2):
`GET /leads?filters={"status":{"$eq":<success_status>},"lastUpdatedTime":{"$gt":C−1s}}&sortProperty=lastUpdatedTime&
sortDirection=ASC&pageSize=100&page=1`. C starter ved `since`. Hver lead → `INSERT IGNORE adversus_success_leads`. Efter
siden er gemt: `C := max(lastUpdatedTime på siden)`. Er siden fuld, hentes næste side med den nye C (keyset, ikke
side-nummer, så leads, der ændres undervejs, ikke forskyder siderne). Har en fuld side ingen fremgang (alle 100 har samme
sekund som C), tages `page=2` af samme filter. Højst 5 kald i fase (a). Et lead, der ændres senere, får ny
`lastUpdatedTime` > C og hentes igen (ufarligt).

**(b) Optagelser i lukkede vinduer på `/recordings.timestamp`** (kun filtrerbar på `timestamp`, kan IKKE sorteres, F004a v2).
Fordi der ikke kan sorteres, bruges side-numre kun inden for et lukket vindue, hvis indhold ikke ændrer sig:
- Cursor R (`adversus-rec`) = vinduets start, gemt som `{"t": <epoch>, "w": <sekunder>}`. Start: `since`.
- Vindue `[R, B)` med `B = min(R + w, nu − LAG)`, `LAG = 10 min`, standard `w = 3600`. Er `B ≤ R`, er der intet at gøre.
- `GET /recordings?filters={"timestamp":{"$gt":R−1s,"$lt":B}}&pageSize=100&page=1..n` til `count < 100` eller
  `page ≥ meta.pagination.pageCount`. Optagelser med `timestamp = B` kommer med i næste vindue (`$gt B−1s`), så der er
  intet hul ved grænsen.
- Mængden `{cdr.id → cdr.timestamp}` slås op i `/calls` med tidsfilter på `start` (sorterbar): `$gt min(cdr.timestamp) −
  M − 1s`, `$lt max(cdr.timestamp) + M`, `M = 5 min`, `sortProperty=start ASC`, alle sider. Kun opkald, hvis `id` er i
  mængden, gemmes (UPSERT). Opkald uden optagelse gemmes aldrig.
- Optagelser, hvis opkald ikke blev fundet: én ekstra `/calls`-søgning med `M = 2 t` for netop deres tidsrum. Findes de
  stadig ikke, logges antallet (kun id'er), og vinduet afsluttes alligevel. Ellers kunne ét uopsporligt opkald stoppe
  hentningen for altid.
- **Cursoren flyttes først, når hele vinduet er gemt:** `R := B`. Rammer kørslen loftet (eller 429) midt i et vindue,
  gemmes det, der er nået (idempotent), men R står stille. Næste kørsel henter vinduet igen og får de samme rækker
  igen (ingen dubletter pga. UNIQUE). Derfor er der hverken huller eller dubletter.
- **Adaptivt vindue:** giver første side `meta.pagination.total > 300` (over 3 sider), halveres `w`, og vinduet startes
  forfra. Blev et vindue afbrudt af loftet, halveres `w` også, så et vindue altid kan blive færdigt inden for ét loft
  (mindst 60 s). Efter et færdigt vindue med under 100 optagelser fordobles `w` igen (højst 3600). Fase (b) fortsætter med
  næste vindue, så længe der er mere end RESERVE kald tilbage, så den indhenter efterslæb.

**AK5 (since):** R og C starter ved `since`, og intet filter kan gå under det: `R − 1s` bruges kun, når R > since, og ved
R = since er den nedre grænse `$gt since − 1s` (= fra og med since). Opkald fundet ved M-margin med `start < since` gemmes
ikke.

## 4. Match til succes-leads, begge veje

- **Opkald gemmes efter leadet (fase b):** `is_success = EXISTS(SELECT 1 FROM adversus_success_leads WHERE lead_id = ?)`.
  Nyt opkald: `transcript_status = 'ventende'` hvis succes, ellers `'ikke_valgt'`. Fase (a) kører først, så leads fra samme
  kørsel tæller med.
- **Lead bliver success efter opkaldet (fase c):** én SQL pr. kørsel:
  `UPDATE calls c JOIN adversus_success_leads l ON l.lead_id = c.lead_id SET c.is_success = 1, c.transcript_status =
  IF(c.transcript_status = 'ikke_valgt', 'ventende', c.transcript_status) WHERE c.source = 'adversus' AND c.is_success = 0`.
  Den fanger også opkald, der blev gemt, før leadet blev hentet, uanset rækkefølgen (AK3).
- Markeringen fjernes aldrig (out of scope). Et opkald i kø eller færdigt røres ikke (IF bevarer status).
- **Lyd (fase d):** `source = 'adversus' AND transcript_status <> 'ikke_valgt' AND (audio_status = 'venter' OR (audio_status
  = 'fejlet' AND audio_attempts < 5))`, ældste først, så længe der er ≥ 2 kald tilbage. `Client::downloadRecording()`
  (redirect kun til `recording_hosts`, AK8) til `.part` → `rename` som Zendesk. Filtypen med `Zendesk\Sync::extension()`.
  Derefter tager den eksisterende kø opkaldet.
- **Manuel knap:** sætter `ikke_valgt → ventende` (se afsnit 2). Lyden hentes ved næste kørsel (højst 10 min), derefter
  transcriberes opkaldet.

## 5. Hvad der ellers rører samme data

- `Calls::where()` (liste, MCP `search_calls`/`list_recent`, zip): får et kildefilter. Flag fra → `source = 'zendesk'`
  (AK9: listen er som før, selv om der ligger Adversus-rækker). Flag til → `visning=succes` (standard): `source = 'zendesk'
  OR is_success = 1`; `visning=alle`: intet filter.
- `Calls::find()` bruges af detalje, lyd og .txt. Med flaget fra giver en Adversus-række 404.
- MCP `getTranscript` og `stats` har egne SQL'er og får samme kildeværn. `callRow()` får `source` og `success`.
- `Calls::transcriptText()`, `fileName()`: "Ticket" giver ingen mening for Adversus. Der står "Lead: <id>", og filnavnet får
  `_lead<id>`.
- `Zendesk\Sync::downloadPending()` er allerede begrænset til `source = 'zendesk'`. `Transcriber.php` og
  `cron/transcribe.php` (H007) røres IKKE.
- `cron/whisper-cron.sh` er projektets egen (ikke låst) og lægger cron-linjerne. Jeg tilføjer `adversus-sync.php` dér. Ejeren
  kører den igen (idempotent). Spørgsmål 5 nedenfor.
- `Client::send()` siger "proben stopper" i loft-/429-teksten, og `test_F004a-AK10` tjekker kun "kaldsgrænsen for
  kørslen (40 kald) er nået". Teksten gøres neutral ("kørslen stopper").

## 6. Hvad er prøvet før

- F004a v1/v2 (`fullstack-ai/F004a_v2.md`): `/calls` kan ikke filtreres på `leadId` (HTTP 400 på DEV), `/recordings` kun
  på `timestamp` og uden sortering, og `$gte` findes ikke (derfor `$gt t − 1s`). Det er grunden til vinduerne i afsnit 3.
- F002's Zendesk-sync bruger en cursor, der kun flyttes fremad, plus 24 t lookback. Lookback er ikke nødvendigt her,
  fordi optagelser hentes på upload-tid, og en sent uploadet optagelse dermed lander i et senere vindue.
- `LEARNINGS.md` har intet om Adversus.

## 7. Hvad jeg ikke ved (og hvad jeg foreslår)

1. **`since` i config.** PROJEKTVIDEN viser `since = 2026-10-01` fra proben, og `AdversusConfig` tolker datoen som UTC
   midnat. Spec og DECISIONS #31 siger start 2026-11-12 00:00 Europe/Copenhagen. **Forslag:** sync tolker `since` som
   dansk midnat og bruger `max(since, 2026-11-12)` som gulv, så en gammel probe-værdi ikke henter 6 ugers historik. Det
   kræver ingen ændring hos ejeren. Alternativet er en ny nøgle `sync_since`, som ejeren skal skrive med
   `vi ~/config/config.ini`.
2. **`cdr.timestamp`'s betydning** (start, slut eller upload) kendes ikke. Derfor margin M = 5 min og en ekstra søgning
   med 2 t for umatchede. Loglinjen viser antallet af umatchede, så det kan måles på DEV.
3. **Agentnavn:** probe-felterne viser kun `userId`. Det vides ikke, om API-brugeren har adgang til `/users/{id}`.
   **Forslag:** gem `userId` i `agent_ext_id` og vis "Adversus-bruger <id>", til et navneopslag er målt. Agentfilteret
   (på `agent_name`) virker så ikke for Adversus i v1.
4. **`duration` vs. `conversation`:** `/calls` har begge. Jeg antager, at `duration` er hele opkaldet i sekunder, og bruger
   den, som spec siger. Hvis feltet er tekst eller millisekunder, viser fixture-testen det ikke. DEV-loggen gør.
5. **Cron-linjen:** "via frameworkets install/deploy-vej". `report.sh install` lægger kun frameworkets scripts.
   Projektets egne linjer lægges i dag af `cron/whisper-cron.sh`, som ejeren kører. Jeg tilføjer linjen dér og skriver
   kommandoen i smoke-testen, medmindre du vil have en anden vej.
6. **Tidsformat:** at `lastUpdatedTime`/`timestamp`-filtrene tager ISO 8601 med `Z` (som proben sender), er målt i F004a.
   Om der er millisekunder i svarene, vides ikke. Parseren tager begge.
7. **Volumen:** 278.000 optagelser i alt, men ikke pr. døgn. Det adaptive vindue håndterer det. Ved meget høj volumen
   (> 100 kald/10 min nødvendige) halter sync efter, men mister intet.
