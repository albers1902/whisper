# System understanding

F003 — MCP-server til Claude Desktop · branch `feature/F003-mcp` · spec `product-ai/F003_v1.md` · impact
`tasks/impact-F003.md` · migration 0004 · flag `[F003_mcp]`. Skrevet 2026-11-11, før kode.

## 1. Hvordan delsystemet virker ende til ende i dag

**Request-kæden (web).**
- `homedir/public_html/.htaccess`: `/health` → `health.php`; alt andet, der ikke er en fil, → `index.php`. Der står
  **ingen** `CGIPassAuth` og ingen `E=HTTP_AUTHORIZATION`-regel i filen.
- `homedir/public_html/index.php`: tjekker `Flags::enabled(App::FLAG)` (F001) FØR alt andet og svarer 404 uden
  session. Derefter `Request::fromGlobals()`. Har klienten en sessionscookie, eller er stien `/login`, startes
  `NativeSessionDriver`; ellers bruges en `ArraySessionDriver` (ingen sessionsfil). `App::handle()` returnerer en
  `Response`; `Throwable` fanges og logges med `error_log` (kun klasse, besked, fil, linje), og klienten får 500.
- `homedir/src/App.php` `handle()`: F001-flag → `dispatch()`: rute (`route()`, faste stier + regex, F002-ruter kun
  med `F002_zendesk` tændt) → metode mod `ROUTES` (405 med `Allow`) → inaktivitets-timeout → `currentUser()` (bruger
  fra DB ved HVER request, aktiv-status og adgangskode-fingeraftryk) → login-redirect (`/login`) → tvunget skift af
  adgangskode → admin-rolle → CSRF ved POST (`Csrf::valid`, felt `_csrf`) → controller. `secure()` lægger CSP,
  `nosniff`, `X-Frame-Options`, `Cache-Control: no-store` på alle svar.
- `homedir/src/Request.php`: værdi med `method`, `path`, `post`, `ip` (kun `REMOTE_ADDR`), `query` og `headers`.
  `fromGlobals()` læser i dag KUN `HTTP_RANGE` ind i `headers`. Der er intet felt til rå body (`php://input`).
- `homedir/src/Response.php`: status, body, headers; `send()` skriver headers og body (eller streamer en fil).

**F002's data, som værktøjerne skal læse.**
- `homedir/migrations/0003_v0.3.0_opkald.sql`: `calls` (bl.a. `id`, `ticket_id`, `direction`, `customer_phone`,
  `agent_name`, `started_at` i UTC, `duration_sec`, `recording_url`, `audio_path`, `transcript_status`) og
  `transcripts` (`call_id` PK, `text` MEDIUMTEXT med FULLTEXT, `segments_json` MEDIUMTEXT). `users.id` er
  `INT UNSIGNED` (`0002_v0.2.0_brugere.sql`), så `mcp_tokens.user_id` bliver `INT UNSIGNED`.
- `homedir/src/Calls.php`: `filter(array $q)` renser query-filtre (`fra`/`til` valideret med round-trip via
  `createFromFormat('!Y-m-d')`, `retning` ∈ inbound/outbound, `agent` ≤120 tegn, `q` ≤200 tegn, `side`).
  `search($f)` = `COUNT(*)` + `SELECT c.* … ORDER BY started_at DESC, id DESC LIMIT 50 OFFSET …`, siden klemmes til
  sidste side. Fritekst: FULLTEXT BOOLEAN med `+ord*` for ord ≥3 tegn, ellers `LIKE`. `transcript($id)` giver
  `text` + segmenter; `transcriptText()` bygger hoved-blok + `[mm:ss]`-linjer; `local()` konverterer UTC → dansk tid.
  `search()` returnerer `c.*` — altså også `audio_path` og `recording_url`, som MCP ikke må udlevere (spec: ingen
  filstier). Udvalget af felter skal derfor være en hvidliste i `Mcp/Tools`.
- `homedir/src/CallPages.php` `transcript()`: kun når `transcript_status = 'faerdig'`; skriver
  `AccessLog::write($uid, 'transcript', ['opkald' => $id])` før svaret.
- `homedir/src/AccessLog.php`: én linje i `logs/adgang.log` (0600). **`action` renses til `[a-z]`** og
  feltværdier til `[0-9a-f]`. Spec'ens format `bruger=<id> mcp <værktøj>` kan derfor ikke skrives med den
  nuværende klasse: `mcp search_calls` bliver til `mcpsearchcalls`. Se spørgsmål 4.

**Flag, throttle og sikkerhedsmønstre at genbruge.**
- `homedir/src/Flags.php`: `enabled()` læser `config/features.ini` for `[app] env`; `override()` til tests.
- `homedir/src/LoginThrottle.php` `begin()`: skriver forsøget FØRST og tæller kun lavere id'er (LEARNINGS F001:
  "Throttle der tjekker før bcrypt og skriver efter, lader parallelle requests igennem"). Samme princip bruges i
  `Mcp/RateLimit`.
- `homedir/src/Csrf.php`: synchronizer-token i sessionen — bruges til `/konto`-formularerne, ikke til `/mcp`.
- `homedir/src/View.php` `account()`: én sektion (skift adgangskode). MCP-sektionen tilføjes her, bag flaget.
- Testløberen `homedir/tests/run.php`: hvert `test_*.php` er én junit-case i egen proces; DB fra `CW_DB_*`;
  proxies peger på en lukket port. `f002_lib.php` har hjælpere (FakeTransport, flag-overrides) jeg kan genbruge.

- `calls`/`transcripts` skrives af cron (`zendesk-sync.php`, `transcribe.php`, `whisper-requeue.php`) og læses af

- `users`: deaktivering (`Users::setActive`) skal slå igennem på MCP-nøgler med det samme → jeg JOIN'er

- `logs/adgang.log` deles med F002's lyd/transcript/zip-linjer.
- `/konto` (POST) bruges i dag til skift af adgangskode; nøgle-handlingerne får egne stier
  (`/konto/mcp-noegle`, `/konto/mcp-noegle/{id}/tilbagekald`), så den eksisterende POST og dens throttling er urørt.
- DECISIONS #1 (MCP er ejerens plan) og #2 (ingen lyd forlader serveren) — `launched/STABLE/DECISIONS.md`. Impact
  noterer, at tekst nu forlader serveren til Anthropic.

## 3. Hvad er prøvet før

- `git log --all --grep=mcp` giver intet; ingen tidligere MCP-kode. ROADMAP.md linje 10 og DECISIONS #1 er de
  eneste omtaler.
- Critic-fund fra F001/F002, som jeg designer efter (`LEARNINGS.md`, `security-critic/F002_v2.md`,
  `qa-critic/F002_v2.md`):
  - hemmeligheder kun som hash, aldrig i log eller fejltekst (nøglen: kun SHA-256 + 8-tegns prefix; ingen
    `error_log` med request-body eller headers);
  - ingen shell (MCP kalder kun PDO);
  - flag tjekket før alt andet (F001 i `index.php`, derefter F003 før auth, DB og body-læsning);
  - ressourcelofter (body-størrelse, rækker ≤50, tekst ≤200 000 tegn, `call_stats` ≤366 dage);
  - throttle der skriver før den tjekker (rate limit som `LoginThrottle::begin`);
  - ingen hukommelses-eksplosion (body læses med loft; transcript-tekst hentes med `LEFT()`/loft i SQL i stedet
    for hele MEDIUMTEXT × 50; uddrag hentes med `SUBSTRING` i SQL);
  - fejl pr. element isoleret (et korrupt `segments_json` giver tom segmentliste for det ene opkald — som
    `Calls::segments` allerede gør — ikke en fejl for hele svaret).

## 4. Svar på spec'ens hand-off-spørgsmål (med kilder)

### 4a. MCP-spec-version og Streamable HTTP

**Fund: den nyeste stabile revision er ikke 2025-06-18, men `2026-07-28`, og den har fjernet `initialize`.**
Kilde: https://modelcontextprotocol.io/specification/versioning ("The current protocol version is 2026-07-28")
og https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning.md: "There is no negotiation
handshake. Every request carries its protocol version"; revisioner `2025-11-25` og tidligere kaldes "Legacy"
(med `initialize`), 2026-07-28+ "Modern". En moderne server SKAL have `server/discover` og kræver headerne
`MCP-Protocol-Version`, `Mcp-Method` og `Mcp-Name` med header/body-validering (`-32020 HeaderMismatch`)
(…/2026-07-28/basic/transports/streamable-http.md, "Request Metadata" og "Server Validation").

Spec F003 kræver `initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call` — det er
legacy-modellen. **Mit forslag: byg en legacy-server på `2025-11-25`** (den nyeste legacy-revision), som spec'en
beskriver. Det virker med moderne klienter, fordi kompatibilitetsmatrixen siger "Dual-era client / Legacy server:
Works … HTTP: the modern request returns a 4xx without a recognized modern error body, and the client falls back to
`initialize`" (…/2026-07-28/basic/versioning.md, "Compatibility Matrix"). Se spørgsmål 1.

Krav fra 2025-11-25, Streamable HTTP (https://modelcontextprotocol.io/specification/2025-11-25/basic/transports):
- Ét endpoint (`/mcp`). Hver JSON-RPC-besked er én POST; body er ÉN request, notification eller response (ingen
  batches — de blev fjernet i 2025-06-18). Klienten sender `Accept: application/json, text/event-stream`.
- Notification eller response som input → **202 Accepted uden body**. Request → `Content-Type: application/json`
  med ét objekt (vi bruger aldrig SSE).
- **GET**: "MUST either return `Content-Type: text/event-stream` … or else return HTTP 405" → 405.
  **DELETE** (afslut session): "MAY respond … with HTTP 405" → 405. Matcher spec'en.
- **`Mcp-Session-Id`**: valgfri ("MAY assign a session ID"). Vi udsteder ingen, så klienten sender ingen. En
  indkommende ignoreres (som 2026-07-28 også anbefaler).
- **`MCP-Protocol-Version`-header**: klienten SKAL sende den efter initialize. Mangler den, "SHOULD assume
  protocol version 2025-03-26". "Invalid or unsupported … MUST respond with 400 Bad Request". Jeg understøtter
  `2025-11-25`, `2025-06-18` og `2025-03-26`. En moderne klient, der sender `2026-07-28`, får 400 med en body, der
  IKKE er en moderne JSON-RPC-fejl (ikke `-32022`/`-32020`) — netop det signal, der får en dual-era klient til at
  falde tilbage til `initialize`.
- **initialize**: hvis klientens `protocolVersion` er understøttet, svares med den; ellers med `2025-11-25`.
  Svar: `protocolVersion`, `capabilities: {tools: {}}` (uden `listChanged`), `serverInfo {name: "whisper",
  version}` (version fra appens CHANGELOG/version — ikke afgjort, ellers `"0.4.0"` fra migrationsnavnet).
- **Origin**: "If the `Origin` header is present and invalid, servers MUST respond with HTTP 403 Forbidden" →
  **403** (spec F003 siger bare "afvises"; jeg bruger 403 som MCP kræver). Se spørgsmål 3 om hvad "sitets egen"
  sammenlignes med.
- Ukendt metode → JSON-RPC `-32601` (HTTP 200, da det er en legacy-session, ikke den moderne 404-regel). Ukendt
  værktøj i `tools/call` → `-32602` (protokolfejl iflg. 2025-11-25 server/tools); fejl i argumenter eller udførsel
  → `result.isError: true` med dansk tekst (spec AK3/AK4).
- `structuredContent` er valgfri; når den bruges, skal `content[0].text` indeholde samme JSON som tekst
  (bagudkompatibilitet i 2025-06-18+). Jeg giver `outputSchema` til de fire værktøjer, så `structuredContent`
  er valideret.

### 4b. Skal `/mcp` undtages fra session, CSRF og login-redirect i `App.php`?

**Ja — og undtagelsen bør ligge FØR `App`, i `index.php`, ikke inde i `App::dispatch()`.** Begrundelse fra koden:
`dispatch()` kører session-timeout, `currentUser()` fra sessionen, login-redirect (303 til `/login`) og CSRF for
ALLE ruter (`App.php` linje 52–100). En MCP-klient har ingen cookie og intet CSRF-token, så den ville få 303.
Hvis man flettede bearer-auth ind i `dispatch()`, skulle hver af de checks have en `/mcp`-undtagelse — det er
præcis den risiko, impact nævner ("Fejl i undtagelsen … kan åbne andre ruter").

Plan:
```
index.php: F001 off → 404 (uændret)
           path === '/mcp' (præcis, efter rtrim '/') → Mcp\Server::handle(Request) ; ingen session, ingen cookie
           ellers → uændret App-kæde
Mcp\Server: F003 off (eller F002 off, spm. 2) → 404 som enhver ukendt sti
            → metode (GET/DELETE/andet → 405 Allow: POST)
            → Origin (403)
            → Bearer → Tokens::authenticate (hash, ikke tilbagekaldt, users.active=1) ellers 401 + WWW-Authenticate: Bearer
            → RateLimit (skriv først, tæl bagefter) ellers 429 + Retry-After
            → MCP-Protocol-Version (400)
            → body (loft 64 KB, Content-Type application/json, gyldig JSON-RPC) → dispatch
```
`App::route()` får IKKE `/mcp`, så med F003 slukket når `/mcp` App og giver den sædvanlige 404 — samme svar som
nu. Ingen session startes for `/mcp`, heller ikke hvis en browser sender en cookie med. `Request::fromGlobals()`
udvides med de få headere, vi bruger (`authorization`, `origin`, `mcp-protocol-version`, `content-type`), og
`index.php` læser body med `file_get_contents('php://input', false, null, 0, 65537)` (loft, så en stor body ikke
fylder hukommelsen). Svar fra `/mcp` får `Cache-Control: no-store` og `nosniff` (genbrug af `App::secure()`-
headers; CSP er ligegyldig for JSON).

`/konto/mcp-noegle` og `/konto/mcp-noegle/{id}/tilbagekald` er derimod almindelige App-ruter (POST), som følger hele
kæden: login, tvunget adgangskodeskift, CSRF. De findes kun i `route()` med F003 tændt.

### 4c. `mcp-remote`: syntaks og låst version

Kilder: npm-registret (`https://registry.npmjs.org/mcp-remote`, felterne `dist-tags` og `time`, hentet
2026-11-11) og README på https://github.com/geelen/mcp-remote (afsnittet "Custom Headers").

- Seneste version er `0.16.6`, udgivet **2026-11-11T05:58Z — i dag**. 0.16.0–0.16.6 er syv udgivelser på ni dage.
- Jeg foreslår at låse **`mcp-remote@0.15.2`** (udgivet 2026-10-20, 22 dage gammel, sidste i 0.15-serien;
  `dist.integrity` = `sha512-3PrXMgjJew6xbZH21D7AbtOoHwhvjWt1IY6wepHjKTZLPSkTPifdMVBFuoxsuF6WK6nUlZIgpSj5o5NscJ+XXw==`).
  Begrundelse: `npx -y` kører koden på brugerens maskine med nøglen i miljøet; en version, der har levet et par
  uger, er en mindre forsyningskæde-risiko end dagens. Se spørgsmål 5.
- 0.15.2 bygger på de nye SDK-pakker `@modelcontextprotocol/client|core|server ^2.0.0` (package.json på tag
  `v0.15.2`). Om SDK 2-klienten taler dual-era (prøver 2026-07-28 og falder tilbage) har jeg ikke kunnet verificere
  uden at hente kildekoden; serveren håndterer begge tilfælde (4a).
- README'ens Windows-advarsel: Claude Desktop (Windows) escaper ikke mellemrum i `args`, så headeren skrives
  **uden mellemrum** og værdien lægges i `env`: `"Authorization:${AUTH_HEADER}"` + `"AUTH_HEADER": "Bearer <token>"`.
  Spec'ens blok (`"Authorization:${WHISPER_AUTH}"` + `"WHISPER_AUTH": "Bearer <nøgle>"`) er altså korrekt.
- Transport: standard er `http-first` (falder til SSE ved 404). Jeg tilføjer **`--transport`, `http-only`**, så en
  404 (fx flag slukket) giver en klar fejl i stedet for et SSE-forsøg. Kræver Node ≥18 (README).
- Ved 401 går mcp-remote i gang med OAuth-discovery (loopback-callback, browser). Vi har ingen OAuth, så en forkert
  eller tilbagekaldt nøgle giver en forvirrende fejl/browser-fane i stedet for "forkert nøgle". Vejledningen på
  `/konto` skal sige: "Får du en login-side eller en OAuth-fejl, er nøglen forkert eller tilbagekaldt — opret en ny."
- Endelig blok (vises én gang efter oprettelse):
  ```json
  {
    "mcpServers": {
      "whisper": {
        "command": "npx",
        "args": ["-y", "mcp-remote@0.15.2", "https://<vært>/mcp", "--transport", "http-only",
                 "--header", "Authorization:${WHISPER_AUTH}"],
        "env": { "WHISPER_AUTH": "Bearer wsp_…" }
      }
    }
  }
  ```

**Alternativ: Claude's egne custom connectors.** Kilde: https://claude.com/docs/connectors/custom/add-unlisted.md
("Authenticate with request headers"). En connector "by URL" kan sende en fast `authorization`-header ("No sign-in"
+ "Request headers", værdien inkl. `Bearer `), men funktionen er "in beta and available to a limited set of
organizations", og forbindelsen går fra Anthropics cloud (serveren skal være offentlig — det er den). Nævnes i
vejledningen som alternativ ("hvis din konto har Request headers"), ikke som hovedvej. Om claude.ai-connectoren
falder tilbage fra 2026-07-28 til legacy, er ikke dokumenteret.

### 4d. Når `Authorization` frem til PHP? (`CGIPassAuth`)

- `shared/SERVERKONTRAKT.md` linje 182 (§3, tabellen over sitets vhost/FPM): "`CGIPassAuth On` | **sat** — uden
  den når `Authorization`-headeren ikke PHP". Linje 322 (fejlsøgning): "401 på Bearer/Basic, koden er rigtig |
  `CGIPassAuth` mangler i vhosten". Kontrakten placerer den altså i **vhosten**, som sysadmin ejer.
- `homedir/public_html/.htaccess` har den ikke, og jeg tilføjer den IKKE: i `.htaccess` kræver `CGIPassAuth`
  `AllowOverride AuthConfig`, og er det ikke tilladt, giver Apache 500 på hele sitet. En
  `RewriteRule … [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]` er unødvendig, når kontrakten siger "sat".
- Koden læser `$_SERVER['HTTP_AUTHORIZATION']` og som fallback `REDIRECT_HTTP_AUTHORIZATION` (sættes, hvis nogen
  senere lægger rewrite-varianten ind; koster intet). Smoke-testen på DEV beviser det: en gyldig nøgle skal give
  200 på `initialize`, ikke 401.

## 5. Designvalg jeg vil tage (rettes gerne)

- **Nøgler:** `wsp_` + base64url(random_bytes(32)) uden padding (43 tegn → 47 i alt). Gemmes: `prefix` = første 8
  tegn (`wsp_xxxx`), `token_hash` = `hash('sha256', $token)` (hex, 64). Opslag på `token_hash` (UNIQUE) — ingen
  sammenligning af klartekst, så timing-angreb er irrelevante; ingen bcrypt nødvendig, da nøglen har 256 bit
  entropi. Formatet tjekkes med regex før hashing (andre værdier → 401 uden DB-opslag).
- **Højst 5 aktive:** tælles og indsættes i en transaktion med `SELECT … FROM users WHERE id = ? FOR UPDATE`, så to
  parallelle POST'er ikke giver 6.
- **Visning én gang:** nøglen er kun i POST-svarets HTML (200, ikke redirect), med `Cache-Control: no-store` (findes
  allerede). Aldrig i session, flash eller log.
- **Tilbagekald:** `UPDATE mcp_tokens SET revoked_at = ? WHERE id = ? AND user_id = ? AND revoked_at IS NULL`
  (egne nøgler; en andens id giver 404 uden at afsløre om den findes).
- **Rate limit:** tabel `mcp_rate (token_id, window_start, count, PK(token_id, window_start))`. Per request:
  `INSERT … ON DUPLICATE KEY UPDATE count = count + 1` for det aktuelle minut, DEREFTER læs `count` → >60 = 429,
  `Retry-After` = sekunder til næste minut. Gamle vinduer slettes 1 ud af 50 gange (som `LoginThrottle`). Tabel
  frem for fil i `var/`: atomisk på tværs af FPM-workere uden låse-filer. (Migration 0004 opretter begge tabeller.)
- **`last_used_at`:** `UPDATE … WHERE id = ? AND (last_used_at IS NULL OR last_used_at < now - 60s)`.
- **Værktøjer:** `search_calls` mapper argumenter til `Calls::filter()`-nøgler og kalder `Calls::search()`; `limit`
  (1–50, standard 20) og `page` håndteres med `array_slice` af de 50 + Calls' egen side. Uddrag (≤300 tegn) hentes
  i én ekstra query `SELECT call_id, SUBSTRING(text, …)` for de returnerede id'er. Hvidlistede felter:
  `call_id, started_at (dansk tid, ISO), direction, duration_sec, agent, customer_phone, ticket_id, transcript_status,
  url (/opkald/{id})` — aldrig `audio_path`, `recording_url`, fejltekster.
  `get_transcript`: kun `faerdig`; tekst bygget som `Calls::transcriptText()` (hoved + `[mm:ss]`), afkortet til
  200 000 tegn med `truncated: true` og en linje "[… afkortet …]". Ukendt/ikke-færdigt id → `isError` "Opkaldet
  findes ikke eller har intet færdigt transcript." uden detaljer.
  `call_stats`: `GROUP BY DATE_FORMAT(started_at, '%Y-%m-%d %H'), direction, agent_name` i SQL (begrænset antal
  rækker: ≤ 8 784 timer × retninger × agenter) og foldning til danske døgn i PHP med `Calls::local()`. Det undgår
  `CONVERT_TZ`, som kræver indlæste tidszonetabeller i MariaDB (ikke målt på serverne).
  Ukendte argumenter → `isError` med dansk tekst (fx "Ukendt argument: foo"); `inputSchema` har
  `additionalProperties: false`.
- **Log:** én `AccessLog`-linje pr. `tools/call` efter udførsel: bruger, værktøj, `opkald=<id>` ved
  `get_transcript`, `antal=<n>`. Aldrig argumenter, tekst eller nøgle. Fejlede værktøjskald logges også (`antal=0`).
- **Fejl:** `Throwable` i et værktøj → `isError` "Der opstod en fejl. Prøv igen om lidt." + `error_log` med kun
  klasse/fil/linje (ingen besked, da en PDO-besked kan indeholde SQL med værdier). JSON-RPC parse-fejl → `-32700`,
  ugyldig request → `-32600`.
