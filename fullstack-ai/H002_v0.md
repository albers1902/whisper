# H002 v0 — System understanding

# System understanding

## 1. Hvordan virker delsystemet ende til ende?
- **Tokenforespørgslen** (`homedir/src/Zendesk/Client.php`, `accessToken()`): bygger en **JSON**-body med
  `grant_type=client_credentials`, `client_id`, `client_secret`, `scope`, `expires_in=3600` og sender
  `POST https://<sub>.zendesk.com/oauth/tokens` med `Content-Type: application/json` og `Accept: application/json`
  gennem `retry429()`. Er status ikke 200, eller mangler `access_token`, kastes
  `ZendeskError('Zendesk afviste OAuth-klienten (HTTP <status>)')`. Svarets body læses (`json_decode`), men
  `error`/`error_description` bruges ikke. Det er netop fejlen, ejeren så.
- **Transport** (`homedir/src/Zendesk/CurlTransport.php`, `request()`): sender headere og body som givet
  (`CURLOPT_POSTFIELDS` med en streng, så curl ændrer ikke formatet). Kun https, ingen redirects.
- **Proben** (`homedir/cron/zendesk-probe.php`): laver en `Client` pr. scope-variant (konfigureret, `tickets:read users:read`,
  `read`) og kalder `accessToken(true)`. Ved `ZendeskError` udskrives `scope "<s>": token afvist (<besked>)`.
  Derefter `getJson()` med det konfigurerede scope; fejl her giver `✘ Talk-export: <besked>` (samme token-fejl, fordi
  `getJson` → `authed` → `accessToken`).
- **Loggen** (`homedir/cron/zendesk-sync.php`): `Sync::run()` (`homedir/src/Zendesk/Sync.php` linje 84–106) fanger
  fejlen; `ZendeskError::getMessage()` går til `sync_state.last_error` (afkortet til 250 tegn, linje 95) og til
  `logs/zendesk-sync.log` via `$log`.

## 2. Hvad rører ellers samme data?
- `ZendeskError`-beskeden vises også på siden: `homedir/src/CallView.php` linje 30–31 skriver `last_error` HTML-escaped
  ("Seneste hentning fra Zendesk stoppede: …"). Den rensede Zendesk-tekst ender altså også i UI'et og databasen, ikke
  kun i probe og log. Docblokken i `homedir/src/Zendesk/ZendeskError.php` kræver: aldrig URL, token, client_secret
  eller sti i beskeden. Rensningen skal derfor gælde for alle tre steder. Det er dækket af AK2.
- `homedir/src/CallPages.php` linje 205 fanger `ZendeskError` uden at vise beskeden.
- Tests mocker HTTP med `FakeTransport` i `homedir/tests/f002_lib.php` (svar pr. metode og URL; `f002_cfg()` laver en
  tilfældig `client_secret`). Testene for H002 bruger samme hjælpere.

## 3. Hvad er prøvet før?
- F002 valgte OAuth client_credentials, fordi Zendesk har fjernet API-tokens (`LEARNINGS.md` linje 9). Scope `read` er
  en accepteret risiko (`launched/STABLE/DECISIONS.md` #14).
- **Zendesks dokumentation** (https://developer.zendesk.com/api-reference/ticketing/oauth/grant_type_tokens/, læst
  2026-11-11):
  - Parametrene "must be formatted as JSON". Eksemplet for client_credentials sender
    `Content-Type: application/json`. Form-encoding nævnes ikke for denne grant type.
  - Den dokumenterede fejl er `400` med `invalid_scope`, når scope ligger uden for klientens tilladte scopes.
    `invalid_client` står ikke på siden. Fejlformatet `{"error","error_description"}` er standard OAuth 2.0
    (RFC 6749 §5.2), og spec'ens AK1 bruger det.
  - client_credentials "is intended only for confidential clients … public clients are not allowed to use this grant
    type".
  - OAuth-klientens `kind` er "public" eller "confidential"
    (https://developer.zendesk.com/api-reference/ticketing/oauth/oauth_clients/). Klientens **identifier** (ikke
    det numeriske `id`) er det, der sendes som `client_id`. Det er min slutning; siden siger det ikke direkte.
- **Konsekvens for spec'en:** dokumentationen kræver JSON. Den hverken kræver eller tillader formularformat for
  client_credentials, så spec'ens betingelse for et fallback til `application/x-www-form-urlencoded` er ikke opfyldt.
  Jeg bygger **intet formular-fallback**. Klienten bliver ved JSON, og proben udskriver `request-format: JSON`.
  Det er spec'ens egen gren ("Engineeren afgør det ud fra dokumentationen"), så spec'en ændres ikke, og jeg fortsætter.

## 4. Hvad ved jeg ikke?
- Hvad Zendesk faktisk svarer på DEV. Sandsynlige årsager til HTTP 400 for alle scopes: klienten er `public` (ikke
  tilladt for client_credentials), `client_id` er sat til det numeriske id i stedet for identifier, eller secret'en
  er forkert. Det afslører rettelsen (`invalid_client` peger på klient/secret/kind; `invalid_scope` på scope).
- Om Zendesk svarer med JSON eller HTML ved en 400 her. Begge håndteres (AK3: generisk tekst med status).
- Om `error_description` nogensinde gengiver client_id eller secret. Det fjernes uanset hvad (AK2).

## Plan (godkendt i spec'en)
- `Client::oauthErrorText(int $status, string $body, list<string> $secrets): string`: læser `error`/`error_description`
  fra JSON. Fjerner client_id, client_secret og token-lignende strenge (lange base64/hex-agtige ord og `access_token`-felter),
  beholder kun printbar ASCII og afkorter til 200 tegn. Er svaret ikke JSON, bruges en generisk tekst med HTTP-status.
- `ZendeskError`-beskeden bliver `Zendesk afviste OAuth-klienten (HTTP 400: invalid_client — Client authentication failed)`.
- Proben: én linje `token-request: POST /oauth/tokens · request-format: JSON`.
- Tests: `homedir/tests/test_H002-AK1_oauth_fejlkode.php`, `…AK2_rensning.php` og `…AK3_html.php`.
